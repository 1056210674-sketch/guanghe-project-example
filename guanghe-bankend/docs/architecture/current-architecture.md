# 光禾AI智能体框架当前架构与扩展边界

日期：2026-10-11。此文随 Java 控制面仓库保存。本文区分本轮代码改造、既有数据模型和后续规划，不代表已经发布到服务器。

## 1. 产品与数据模型

只有普通用户 USER 和管理员 ADMIN。用户可以替多个客户工作，例如“小行星咖啡店”“艾尼亚科”各建一个项目。客户不是登录成员，也没有代理组织、邀请员工或组织角色。

- 账号是数据所有权边界：业务数据依 `user_id` 隔离，不由浏览器传来的用户字段决定。
- 项目是同一账号下的客户资料边界：聊天、品牌事实、报告、内容和素材不得跨项目串用。
- 账号级记忆只承载明确适用于全部项目的表达偏好；客户品牌事实进入项目级记忆。
- 管理员治理接口与普通用户接口分开验权；管理员角色不是绕过来源、投稿确认和计价规则的理由。

Agent 的 `capabilities/allowedTools` 是程序执行边界，不是第三种用户角色或组织权限。它防止只读助手写数据、创作助手读取无关客户资料；用户侧仍只有 USER/ADMIN 两个角色。

旧表 `business_space` 继续承载项目及个人创作存储。它是历史物理表名，不意味着产品仍有“经营空间”或组织租户。仅为改名重建表会破坏大量引用，本轮不做这类无收益迁移。

## 2. 职责与执行链路

```text
Web：选择项目、输入请求、引用资料
  ↓ /api/v1
Java：身份/项目归属 → 会话绑定 → 冻结 Run 上下文与有效能力
  ↓ 已有签名内部协议
Python：校验运行清单 → 共享循环 → 模型与工具 → 流式事件
  ↓ 工具动作回到 Java 再次验权
Java：用户原文/当前权限/价格/幂等 → 任务与业务结果
  ↓ 既有队列与 Worker 执行、结果验收
Web：展示受理、进行中、完成或失败，不把受理等同于完成
```

Java 保留模块化单体，不拆出新的租户/权限微服务。Python 复用当前 RunManager、Harness、模型网关、工具注册与执行器；不增加第二套 Agent 框架。长任务沿用现有 Worker 和 Java 任务状态机。

## 3. 本轮收拢的扩展点

| 问题 | 当前处理方式 |
| --- | --- |
| 两端各自写死 Agent 名单、版本和权限 | 共用受控 `runtime-catalog.json`，跨仓校验内容与 SHA256 |
| 工具读权限隐式等于记忆写权限 | 工具声明所需能力，Agent 同时受能力上限和工具白名单限制 |
| GEO 业务策略混在通用循环 | `NativeAgentLoop` 与 `app/agents` 的 GEO 行为分离 |
| Worker 默认取第一个 Profile | 清单明确指定 `workerProfileCode`，缺配置直接失败 |
| 新 Agent 要改前端身份判断 | 常用聊天入口按 capabilities 显示；形象仍可按身份配置 |
| Java 代码持续追加文章 Prompt 版本 | 精确版本集合移入清单，与 OpenAPI/Python 消费者做一致性检查 |
| “1.0.0”不能识别执行发布 | 新 Run 冻结 `executionRelease` 与 `catalogHash`，Python/Java 均校验 |

清单源在 `guanghe-agent/app/agents/runtime-catalog.json`，Java 镜像在 `src/main/resources/contracts/agents/runtime-catalog.json`。SHA256 对 UTF-8 内容规范化 CRLF 为 LF 后计算，不对 JSON 排序。清单还钉住 Prompt Bundle 的版本和规范化哈希，避免只改提示词内容却沿用原发布标签。

清单是代码审查后的发布资源，不从用户输入、URL、模型输出或数据库脚本动态加载类。`runtimeKind`、业务策略和工具仍为受控集合。

## 4. 版本、权限与兼容

三个版本概念不能混淆：

1. Agent 定义版本：数据库内不可修改的 `agent_key + version`，安装及会话绑定引用它。
2. 执行发布版本：本次部署实现，声明在清单中；每次新 Run 冻结执行发布和清单哈希。
3. Prompt Bundle 版本与哈希：本次部署实际提示词，清单启动校验并进入既有追踪。

当前不是“一条历史会话永远使用创建当天的全部代码和提示词”。旧会话的定义/项目绑定不变，新 Run 使用当前受控发布；同一 Run 不可在两端版本不同的情况下静默继续。不匹配应明确失败并由用户发起新轮次，不能暗中重复付费任务。

兼容只允许既有 `geo/creative/summary@1.0.0`。旧定义较粗的能力通过显式 `legacyCapabilityGrants` 映射；未知 Agent、新版本不自动继承。新 Run 的完整能力快照不再重复扩权。执行工具使用冻结能力与当前有效权限交集，安装停用/删除等控制继续生效。

读取资料不自动获得写品牌、写记忆、监测、生成媒体或投稿能力。前端按钮不是安全边界，两端仍验权。用户原文、归属、最终投稿确认、积分锁定和外部提交幂等规则不因重构绕过。

旧混合工作流的签名入口也执行同一权限检查，不因它是内部接口就默认放行。当前三个内置 Agent 都不具备混合工作流要求的全部能力，因此不会经该入口新建跨领域编排；GEO/创作各自的原生工具链保留。未来开放混合编排须显式注册对应能力，不能借 GEO 身份调用生图/视频工具。历史工作流上下文裁剪保留完整身份和版本信息。

绑定项目的聊天从消息受理、上下文快照到资料搜索/回放都校验同一项目；浏览器仍不能通过旧 `selectedSpaceId` 参数切入另一个客户。无项目聊天的显式项目发现流程不等于已获准把客户资料并入当前项目。

### 当前代码的职责落点

- `conversation/RunToolAuthorizationService`：实时工具入口的共同授权。`RunActionService` 和 `RunResourceService` 都先检查当前账号、锁定 Run、校验安装及能力，再处理自己的业务；历史回执不能跳过当前授权。两入口原有事务和回执语义不合并。
- Python `app/agents/geo_continuation.py`：仅解释 Java 返回的 GEO 续接证据，维护当前 Run 的一次性状态；不能自己调用 Java、模型或扣费。`NativeTools` 仍是唯一原生工具执行入口，共用原有预算、幂等与未知提交保护。
- Web `features/agent-platform/installedAgent.ts`：聊天、资产、智能体库和选择器统一按 `agentKey + agentVersion` 找已安装定义，不借新版状态或能力。历史聊天仍显示自己的冻结身份和内容。

只读授权链的预期 `BusinessException` 不把外层资源事务标为 rollback-only，避免正常拒绝变成 `UnexpectedRollbackException`。此规则限定在 Run 上下文、安装权限检查、冻结知识复核和记忆上下文读取；没有全局改变异常规则。动作写事务仍回滚，技术异常仍回滚，安装/定义的 SHARE 锁仍跟随原外层事务。

续接同时要求领域策略与工具授权：文章为 `continuationPolicy=geo-article`，监测为 `contextPolicy=geo-brand`。给其他 Agent 声明文章/监测能力，不会自动附送 GEO 的“好/提交”续接规则。明确的新文章请求仍走原有语义准入，不能用策略拆分恢复关键词路由。

Java 用户目录返回每个 key 的最新可见条目，以及该用户已安装的精确旧版本，保持最新版在前；安装 ID 只挂在精确版本上。Web 仅对“智能体库”卡片按 key 去重，安装、聊天和资产必须使用完整目录。`WITHDRAWN` 表示不再允许新添加，但已有安装仍可交互使用；既有自动监测调度只允许 PUBLISHED 的政策不变。`DISABLED` 表示停止执行，不能借同 key 新版恢复。Java 运行准入仍会独立检查可见性、受控运行清单和有效能力。

新增业务优先放到已有领域服务。只有已有两个真实入口重复维护同一规则时才提取公共模块；不为了让大文件看起来变小就新增一层转发，也不因为增加一个 Agent 就复制完整执行链。

## 5. 数据库处理

现有 `agent_definition_version`、`agent_installation`、`conversation_agent_binding` 已表达“版本 → 安装 → 会话”；复合外键包含用户归属，不新建平行表。记忆、摘要、文章版本、Run/任务状态仍由 Java 各业务模块维护。

本轮执行元数据放入既有 Run JSON 授权快照，不修改已应用 Flyway，不删表、清库或引入成员表。今后新增内置 Agent 定义要追加迁移，不 UPDATE 已发布定义来替换能力或版本含义。

## 6. 明确不做的范围

用户已明确将自建智能体列为长期目标，当前不做设计器、私有 Agent 表、在线 Prompt 编辑、配置发布流程或通用插件平台，也不把这些计入当前交付缺口。接入指南只服务开发同事新增受控的内置智能体。

保留当前清晰边界即可：Java 管业务和归属，Python 管执行，受控清单决定可运行代码与工具。以后需求明确时再设计用户配置，不为未来需求增加当前运行分支或数据库结构。

## 7. 验证与发布

功能检查走真实应用装配、循环、事件和授权；确定性网关/API 桩不证明真实模型文案质量。第四 Agent 应走同一运行入口，不只测孤立解析函数。

发布记录三仓完整 commit、清单/Bundle 哈希、构建产物和功能结果。未跟踪/未提交源码时可做开发检查，但 release 模式必须拒绝。禁止覆盖 JAR 中几个 class 后称为可复现发布。

见 [接入指南](adding-an-agent.md) 与仓库 `scripts/run-cross-repo-stability-gate.ps1`。共享数据库、部署和付费调用单独记录，不由本地检查自动触发。
